## 兩種介面

- **Inline visualizer 路線圖**是長期、多階段、多批次，或需要首次公開對齊的 CER
  任務的標準進度面，
  不要求使用者每次介入。版面、階段數和附加欄位按項目需要動態決定，不使用
  固定四格或固定表格代替實際任務資訊；最低內容依「顯示優先序」。
- **ASCII 小熊四色卡**是 checkpoint 訊號，只回答「現在是否需要使用者預覽、決定、
  處理阻礙或驗收」。它不代替路線圖，也不作持續進度表。

同一訊息可同時有兩者，但內容不重複：路線圖顯示全局位置，卡片只說明本次停點。

## Inline visualizer 標準時機

1. C 判定任務會跨多階段或多批次，或屬新產品、流程、設計、內容、體驗型成果而
   需要首次公開對齊時，在第一個實際批次前顯示初始路線圖。
2. C 讀回並接納一批成果，而階段、批次或下一停點因此改變時，更新路線圖。
3. 使用者裁決、實際新限制或 R 的反證令方向／範圍／交付形狀、風險或接納狀態
   實質改變時，先顯示與上一版的差異，再更新路線圖。
4. 階段交付、技術驗收、用途校正或收工時，顯示相應終態。

普通內部讀檔、E1 子步驟、輪詢結果、未經 C 裁決的候選，以及沒有改變使用者
視角進度的細節，不更新路線圖。進度只來自 direct-push 後的有界讀回與 C 裁決。

## 固定生命週期卡

每次顯示任何 lifecycle 或 checkpoint 小熊卡前，重新讀取本 Skill 根目錄
`VERSION`。穩定 semver `X.Y.Z` 顯示為 `vX.Y.Z`；缺失、不可讀或格式錯誤時
顯示 `version unverified`。以下卡片中的 `{package_version}` 是模板佔位；
輸出前必須以當次讀到的 `VERSION` 完整替換，絕不可把佔位文字原樣顯示。
每張卡必須作為獨立 fenced `text` code block 輸出；不得放入 bullet、引用、
普通段落或與其他文字同一個 Markdown 區塊。

```text
   ()_()   CER 工作法 v{package_version}
  ( o.o )  🔵 CER 已啟動
   ( ^ )
```

每次成功接受 `CER-start` 都使用以上固定開眼啟動卡，包括簡單單批任務。啟動
卡保留完整三行 ASCII 小熊；版本在第一行，狀態在第二行，第三行只保留小熊底線。

成功 `/CER-stop` 使用固定閉眼停用卡：

```text
   ()_()   CER 工作法 v{package_version}
  ( -.- )  ⚪ CER 已停用 · CER inactive
   ( ^ )
```

成功 `/CER-close` 使用固定閉眼收尾卡：

```text
   ()_()   CER 工作法 v{package_version}
  ( -.- )  🟢 CER 已收尾 · writer closed
   ( ^ )
```

閉眼卡是已驗證終態，不是意圖回執。停用卡只可在沒有 active writer 或 writer
已停止且必要讀回完成後顯示；收尾卡只可在 `writer closed`、必要讀回，以及該輪
可核實 C／E／R title 的 cycle 編號加 `✓` 或 `title sync warning` 已讀回後顯示。
閉眼收尾卡只代表 writer close／必要讀回完成，不代表 title sync 全綠。任一證據不足時使用開眼紅色 blocker 卡：

```text
   ()_()   CER 工作法 v{package_version}
  ( o.o )  🔴 重大阻礙 · checkpoint blocked
   ( ^ )
```

## 其他固定停點卡

生命週期卡以外的停點沿用開眼 ASCII 小熊，同樣使用獨立 fenced `text` code
block；版本在第一行，狀態按場景替換在第二行。若版本無效，同樣顯示
`version unverified`。

- `🟡 方向抉擇`
- `🔴 重大阻礙`
- `🟢 階段性交付／最終驗收`

## 小熊卡使用時機

CER 是連續閉環，不代表每個小步都發卡：

1. 每次成功接受 `CER-start`，先用一次固定 `🔵 CER 已啟動` 卡作啟動回執；
   單批也必須顯示。長期／多批次或需要首次公開對齊的任務，由同訊息 inline
   路線圖承載完整階段資訊。
2. 重大方向、範圍、交付形狀、成本、知識來源或驗收標準需要使用者取捨時，
   用 `🟡 方向抉擇`。
3. 通訊鏈、threadId 或平台等價座標、權限、真源、知識底座、平台能力或安全條件
   不足，不能可靠繼續時，用 `🔴 重大阻礙`。
4. E1 完成可觀察階段、C 已讀回裁決，或 R 完成高風險反證後形成使用者可驗收
   成果時，用
   `🟢 階段性交付`。
5. 成功 `/CER-stop` 顯示固定閉眼 `⚪ CER 已停用` 卡；成功 `/CER-close` 顯示
   固定閉眼 `🟢 CER 已收尾` 卡。一般最終驗收仍可用開眼
   `🟢 最終驗收`，不得冒充生命週期終態。

普通內部讀檔、低風險小修、E1 子步驟、普通批次接納、R 完成但沒有形成用戶
停點，以及已清楚不需使用者介入的下一步不發卡；需要時只更新 inline 路線圖。

## 顯示優先序

Inline 路線圖最少顯示：可驗收終點；有次序的階段及已完成／目前／待辦狀態；
整體進度；目前動作及已核實證據或 blocker；C／E1／R 狀態；下一停點；知識性
任務才加知識底座狀態。首次公開對齊另顯示範圍／排除、關鍵假設、最小可觀察
成果、技術驗收與用途校正是否適用，以及是否需要使用者決定。停點卡只把當前
情況壓成「預覽、決定、停下或驗收」。
兩者都只派生自既有 project plan／progress 或已核實執行狀態，不是第二套計劃
或進度。

1. Codex 有可調用的 in-conversation visualization 能力時，預設建立 inline HTML visualization，並使用該能力要求的正式呈現指令，例如 `::codex-inline-vis{file="..."}`。
2. Mermaid 不算完成第一層要求。只有 inline visualization 能力不存在、不可調用、不可寫入其指定視覺目錄，或實際呈現失敗時，才使用 Mermaid。
3. Mermaid 也不可用時，才使用固定 Markdown／純文字。
4. 降級時用一句話明示原因；不可靜默降級，也不可因視覺能力缺失阻塞項目。

純文字 fallback：

```text
目標：<終點>
範圍／排除：<本次會做／不做>
關鍵假設：<已確認／安全推定／需要裁決>
[公開對齊：<已確認／安全推定／需要裁決>]
[✓] 已完成 → [● 現在] 當前階段 → [○] 後續階段 → [○] 最終交付／收工
目前：<一句>
最小可觀察成果：<下一次你會看見>
驗收：技術驗收=<條件／不適用>；用途校正=<條件／不適用>
下一停點：<一句>
知識底座：<已確認／缺來源／不適用>
角色：C=<狀態>｜E1=<狀態>｜R=<未建立／驗收中／完成>
```

## 角色顯示邊界

路線圖與生命週期卡只顯示正式 C、E1、R，以及接管時的 E2。平行候選生產者是
C 的內部按需能力，不加入角色欄、生命週期卡、使用者設定或獨立進度；只有其
缺失證據成為實質 blocker 時，才用一般風險語言呈現結果。

## 路線圖真源

只用最高可用權威來源，不建立第二份進度：

1. 目標專案已有權威進度／Roadmap 時，由它派生。
2. 只有已確認計劃而未有進度來源時，由計劃加已核實執行狀態暫態派生。
3. 未有計劃時，由使用者本次需求與已核實角色／阻礙事實暫態派生，標示「初始／待收斂」。

若同時使用 `$project-context-workflow`，只讀取其已確認計劃與進度，不重做五步或
建立第二道相同共識關卡。

普通工程細節不發卡。方向或交付形狀取捨用 🟡；可靠性 blocker 用開眼 🔴；
可觀察階段成果與一般最終驗收用開眼 🟢。只有已證明終態的 stop／close 使用
閉眼卡。普通批次進度只更新 inline 路線圖。
